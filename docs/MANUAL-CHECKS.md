# Ручные проверки перед запуском

Автотесты (`go test ./...`, `npm test`, `tests/compat/run.sh`) покрывают сервер, шифрование
и совместимость. Ниже — то, что можно проверить только на сервере, доступном из интернета:
превью ссылок в мессенджерах, Lighthouse на настоящем домене и заголовки за прокси.

## 1. Превью ссылки не расходует секрет

Боты Telegram, Slack, WhatsApp и других мессенджеров открывают ссылку, чтобы построить превью.
Страница `/s/<id>` на GET не обращается к хранилищу, а шифротекст выдаётся только по POST после
нажатия «Показать секрет». Проверить это нужно на стейдже или на проде: боты должны дотянуться
до сервера.

### Telegram

1. Откройте стейдж, создайте секрет без пароля, например текст `preview-test-1`.
2. Скопируйте ссылку и отправьте её в «Избранное» (Saved Messages) в Telegram.
3. Дождитесь превью. Ожидается карточка с заголовком «Вам отправили секрет — Encrypt.One»
   (или на языке браузера отправителя) и OG-картинкой. Текста секрета в превью быть не должно.
4. Подождите ещё минуту: Telegram иногда запрашивает страницу повторно.
5. Откройте ссылку в браузере на другом устройстве или в приватном окне. Ожидается экран
   «Вам отправили секрет» с кнопкой «Показать секрет», а не «Этот секрет уже недоступен».
6. Нажмите «Показать секрет»: должен появиться текст `preview-test-1`.
7. Откройте ссылку ещё раз: теперь ожидается «Этот секрет уже недоступен».

### Slack

1. Создайте второй секрет, например `preview-test-2`.
2. Вставьте ссылку в любой канал или в личные сообщения самому себе и отправьте.
3. Дождитесь разворачивания превью (unfurl).
4. Повторите шаги 5–7 из проверки Telegram.

### Что смотреть в логах сервера

Страницы в лог не пишутся, только запросы к API. Пока бот строит превью, строк с
`"route":"/api/secrets/:id/reveal"` до вашего нажатия «Показать секрет» быть не должно.
В логе не должно быть id секрета, токена, IP и фрагмента ссылки после `#`.

## 2. Lighthouse на мобильном

Локально (последний прогон: производительность 97–100, доступность, лучшие практики и SEO — 100):

```bash
npx lighthouse@12.6.1 https://staging.encrypt.one/ --form-factor=mobile --only-categories=performance,accessibility,best-practices,seo --view
```

Проверьте `/`, `/ru/`, `/uk/password-generator/`, `/how-it-works/`, `/privacy/` и
`/s/<любой id>`. На `/s/` и `/m/` SEO будет около 66: единственная непройденная
проверка — «Page is blocked from indexing», это ожидаемый `noindex`.

## 3. Заголовки за прокси

```bash
curl -sI https://staging.encrypt.one/ | grep -iE 'content-security|strict-transport|referrer|x-content-type|permissions|frame'
curl -sI https://staging.encrypt.one/s/AbCdEfGhIjKlMnOpQrStUv | grep -i x-robots-tag
```

Ожидается CSP без `unsafe-inline`, HSTS, `Referrer-Policy: no-referrer`, `nosniff`,
`Permissions-Policy`, `frame-ancestors 'none'` и `X-Robots-Tag: noindex, nofollow` на `/s/`.
Если прокси добавляет свои заголовки, они не должны ослаблять CSP.

Убедитесь, что прокси перед сервером передаёт `X-Real-IP` с адресом клиента. Иначе ограничение частоты будет
считать всех посетителей одним IP.

## 4. Старые ссылки после выкладки

1. До выкладки создайте на текущем сайте два секрета: без пароля и с паролем.
2. Выложите новую версию на то же дисковое хранилище (`DISK_STORAGE_PATHS`).
3. Откройте обе старые ссылки: они должны открыться на новой странице получателя.
   CryptoJS загружается только для них (вкладка Network: `crypto-js.*.js`).
4. Через 8 дней после выкладки удалите код старого формата: поиск по `LEGACY-V1` в репозитории.
